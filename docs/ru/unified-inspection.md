# Единая проверка публикации

## Одна команда с явной областью

В 0.3.0a1 добавлена `publication-opsec-inspect DIRECTORY`: она распределяет UTF-8 текст и поддержанные DOCX/PPTX/XLSX в общий JSON. Подготовленная копия читается без изменений. Установите пакет и дополнительные зависимости валидации по [инструкции](installation.md). Отчёты сохраняйте вне области, приватные политики — вне публикуемых материалов.

```bash
publication-opsec-inspect prepared-materials --policy policy.local.json > publication-report.json
publication-opsec-validate publication-report.json
```

Первая команда возвращает 0 без находок/пробелов в заявленной области, 1 при находках, возможно с пробелами, 2 при неполной/неверной проверке без находок. Валидатор сохраняет смысл кодов и возвращает 3 при неверном отчёте/недоступной валидации. Shell обычно останавливается на ненулевом коде; сохраняйте отчёт отдельным шагом артефактов после ошибки, но не скрывайте ошибку ради публикации.

## Распределение и лимиты

Обычные поддержанные файлы копируются во временное текстовое/Office дерево. Текст проверяют пять существующих правил, Office — ограниченный профиль документа. Относительные пути сохраняются. Неизвестные расширения, PDF, изображения, архивы, ссылки и специальные файлы остаются пробелами; исключённые Git/cache-каталоги также не дают полного покрытия. Пустой вход не успешен.

Общие лимиты: 1 000 файлов, 1 000 каталогов, 50 000 000 прочитанных байтов, 100 Office-документов, 10 000 находок верхнего уровня. На копируемый файл: 2 000 000 байтов текста или 8 000 000 Office. XML-лимиты отдельные. Это не жёсткая квота памяти/CPU. Счётчики/копирование не доказывают неизменность источника: используйте стабильное подготовленное дерево. Обычное удаление временных данных не гарантирует стирание.

## Дополнительный Gitleaks

Специализированный поиск запрашивается явно и не заявляется по умолчанию:

```bash
publication-opsec-inspect prepared-materials --gitleaks /absolute/path/gitleaks --engine-sha256 VERIFIED_BINARY_SHA256 > publication-report.json
```

Заполнитель хеша нужно заменить проверенной суммой бинарника. Требуются версия 8.24.2 и существующие меры адаптера. `secrets_requested: false` означает отсутствие запроса движка, а не полную проверку секретов. При запросе проверяется только подготовленный текст. Каждый Office-документ получает `document_secret_engine_not_tested`: общий результат остаётся неполным даже после успешных обычных Office-проверок. Отсутствие/сбой движка и неполная конфигурация видимы. Основные Action/hook остаются текстовыми; для смешанных публикаций запускайте новый CLI отдельным шагом.

## Общий контракт

`bundle-0.1` содержит область/версию, secrets_requested, coverage_complete, счётчики/лимиты, nullable text_report, отчёты документов, nullable secrets_report и coverage_gaps общего запуска. Вложенные ответы сохраняют версии. text_report равен null, если текста не было; область только из документов может успешно завершить свой XML-профиль. Полнота возможна только при завершении общего запуска и всех запрошенных проверок. Код 1 не доказывает полноту. Пути остаются чувствительными метаданными, хотя совпадения скрыты.

[Схема общего ответа](../../schemas/bundle-0.1.schema.json) и [валидация всех отчётов](all-report-validation.md) описывают контракт потребителя. PDF/OCR, произвольные архивы, онлайн-проверка токенов, автоматическая очистка и разрешение публикации отсутствуют.
