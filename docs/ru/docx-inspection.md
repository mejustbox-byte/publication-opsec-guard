# Проверка DOCX: XML-текст и идентифицирующие метаданные

## Что делает команда

`publication-opsec-documents` локально и без изменений проверяет один `.docx`. UTF-8 XML-текст и атрибуты проверяются правилами PUB-001–PUB-005; DOC-001 отмечает выбранные непустые идентифицирующие метаданные. Это первый подцикл формата M6, а не универсальная поддержка Office/PDF/архивов. Текстовый сканер, адаптер секретов и Action/hook не запускают эту команду автоматически.

DOCX содержит отдельные XML-части. Требуются `[Content_Types].xml`, `_rels/.rels`, `word/document.xml`, корневой WordprocessingML-элемент, немакросный тип основного DOCX-содержимого и главное отношение. Это ограниченный профиль пакета, а не полная валидация ECMA/ISO и не рендеринг Microsoft Word. См. [описание структуры Microsoft](https://learn.microsoft.com/en-us/office/open-xml/word/structure-of-a-wordprocessingml-document).

## Установка и запуск

Установите Guard 0.2.0a5 из проверенной копии по [руководству установки](installation.md). Дополнительная библиотека парсинга и Microsoft Office не нужны. Проверяйте неизменяемую подготовленную копию, сохраняйте отчёт вне каталогов последующих проверок:

```bash
publication-opsec-documents prepared.docx --policy policy.local.json > document-report.json
```

`--policy` необязателен и использует существующую строгую UTF-8 политику маркеров. Код 1 — находки, возможно вместе с пробелами; 2 — неполная/некорректная проверка без находок; 0 — нет находок и записанных пробелов в заявленной XML-области. Он не доказывает безопасность визуального документа и каждого вложенного представления. Обычный Word-файл может содержать автора и давать DOC-001.

## Извлечение и доказательства

Разбираются все доступные `.xml`/`.rels` части. В абзацах transitional WordprocessingML объединяются runs с текстом `w:t`, `w:delText`, `w:instrText`: адрес, разделённый форматированием, может быть найден. Текст других элементов и значения атрибутов проверяются отдельно. Колонтитулы, сноски и комментарии охватываются, если представлены читаемыми XML-частями. Атрибуты включают адреса ссылок; переходы не выполняются.

Находка содержит basename документа и ZIP `part_id`. PUB-находки имеют `evidence.kind: extracted_line` и строку с единицы во временном извлечённом представлении: **это не страница Word и не исходная строка XML**. DOC-001 имеет `kind: identity_metadata` без строки. Источники: непустые creator, lastModifiedBy, Company, Manager под docProps и атрибуты author/initials частей word/comments. Это сигнал для оценки контекста: синтетические имена автора/инструмента могут быть намеренными ложными срабатываниями.

Совпадения и значения метаданных не выводятся. Имена файлов и частей остаются видимыми. Автоматическое удаление метаданных, замена ключей и редактирование документа не выполняются.

## Лимиты и отклонение входов

| Лимит | Значение |
|---|---|
| ZIP input | 8,000,000 bytes |
| ZIP entries | 1,000 |
| Uncompressed part | 2,000,000 bytes |
| XML total | 16,000,000 bytes |
| Declared compression ratio | 100 |
| XML depth per part | 64 |
| XML elements per part | 100,000 |
| Findings | 10,000 |

Принимаются ZIP-части stored/deflated. Отклоняются шифрование, ZIP-симлинки, повторяющиеся имена, абсолютные пути/обход каталогов, обратные слеши, двоеточия и неоднозначные имена. Части читаются ограниченными потоками; пути архива не используются для распаковки на диск. DTD/ENTITY, UTF-16/NUL XML, некорректный XML и превышение глубины/числа элементов остаются непроверенными. UTF-8 BOM принимается.

ZIP читается с лимитом в память, XML-деревья ограничиваются, для существующего движка правил используется приватный временный текстовый файл. Это не жёсткая квота общей памяти или CPU. XML/ZIP-библиотеки требуют поддерживаемого Python; минимум в метаданных пакета — граница совместимости, а не гарантия уровня исправлений безопасности. См. [безопасность XML Python](https://docs.python.org/3/library/xml.html) и [ZIP](https://docs.python.org/3/library/zipfile.html).

## Пробелы покрытия и решение

| Причина | Значение |
|---|---|
| uninspected_zip_metadata / xml_comments_or_processing_instructions | ZIP-комментарии/дополнительные метаданные или XML-комментарии/инструкции присутствуют, но не проверены |
| unsupported_part | Изображения, встроенные бинарные файлы, VBA и прочие не-XML данные не проверены |
| external_reference | Отношение ведёт за пределы пакета; содержимое не загружалось |
| archive_size_limit / part_count_limit | ZIP превышает заявленную область |
| part_size_or_ratio_limit / total_xml_bytes_limit / part_read_limit | Ограниченная распаковка/чтение не позволили завершить проверку |
| encrypted_part / unsupported_compression | Профиль не поддерживает такое содержимое |
| unsafe_or_duplicate_part | Имена/тип частей неприемлемы |
| invalid_or_unsupported_xml | Некорректный XML, неподдержанный UTF-8, DTD/entity или превышение лимитов |
| invalid_ooxml_package | Нет обязательных частей/корня/типа/главного отношения или они несогласованны |
| extracted_text_incomplete | Основной сканер не завершил проверку извлечённого текста |
| invalid_input_policy_or_package | Ошибка входа, политики, чтения ZIP или лимита находок |

Находки совместимы с пробелами: читайте оба массива. Читаемый XML вокруг изображения не делает изображение безопасным. Внешние ссылки могут быть легитимны, но покрытие внешнего содержимого недоступно. DOCM, старый DOC, PDF, XLSX, метаданные изображений/OCR и произвольные ZIP не поддерживаются.

## Схема ответа

Отдельный формат `documents-0.2` содержит версию схемы/инструмента, область, basename, покрытие, счётчики, действующие лимиты, находки и пробелы. Поставляемая [JSON Schema](../../schemas/documents-0.2.schema.json) проверяет структуру, но не подлинность источника и безопасность публикации. Основной CLI `publication-opsec-validate` теперь поддерживает этот формат.

`coverage_complete` означает успешную обработку ограниченной области XML-текста/выбранных метаданных. Это не семантическая проверка отношений, не обнаружение всего смысла скрытого/custom XML, не полнота визуального содержимого и не гарантия поиска каждого секрета. Strict OOXML, необычное место основной части, редкие допустимые кодировки/методы сжатия могут консервативно отклоняться.

## Проверки и следующие форматы

Четырнадцать тестовых методов создают синтетические ZIP-пакеты: чистая структура; индикаторы в разных runs; скрытие маркеров; метаданные автора/комментариев; колонтитул/внешняя ссылка; изображения/вложения; небезопасные/повторные/симлинк-части; DTD/глубина/кодировки; объём/число/коэффициент сжатия; неверные пакеты; неизменность источника/политика; лимит находок/отсутствие сети; состояния схемы; CLI 0/1/2. Они выполняются на трёх платформах CI. Установка в чистое окружение также проверяет новую команду.

Фикстуры не доказывают рендеринг после сохранения в Microsoft Word и все реальные генераторы DOCX. Следующему формату нужны отдельные выбор парсера, модель угроз, лимиты, корпус и честные состояния покрытия. Поставка DOCX не означает автоматическую готовность PDF/остальных Office-форматов.
