# Валидация отчёта: схема, согласованность и интеграция

## Для чего нужен валидатор

Потребитель должен отличать чистую проверку поддерживаемого текста, находки, неполное покрытие, ошибку запуска и некорректный ответ. Разбор JSON сам по себе этого не обеспечивает. `validate_report.py` проверяет контракт 0.2 по поставляемой схеме, затем межполевые условия и вычисляет код выхода сканера.

Валидация читает готовый отчёт. Она не проверяет исходники повторно, не открывает пути `asset_id` и не обращается к сервису. Она не доказывает, что отчёт создан Guard или что счётчики относятся к настоящей исходной копии. Поддельный, но внутренне согласованный отчёт может пройти: подпись, хеши исходников и доказательство происхождения не поставляются.

## Установка и окружение

Сканер `guard.py` по-прежнему использует только стандартную библиотеку. Отдельный валидатор использует `jsonschema==4.26.0` и транзитивные зависимости с зафиксированными версиями в [requirements-validation.txt](../../requirements-validation.txt). Для конфигурации CI используйте Python 3.13. Локальная разработка также проверялась на Python 3.12; это не матрица всех минорных выпусков и архитектур.

Создайте отдельное окружение:

```bash
python3 -m venv .venv
```
Активируйте его командой `source .venv/bin/activate` в POSIX либо `.venv\Scripts\Activate.ps1` в PowerShell. Затем установите зависимости и проверьте готовый чистый ответ:

```bash
python3 -m pip install -r requirements-validation.txt
python3 -m pip check
python3 validate_report.py examples/reports/valid/clean.json
```
Последняя команда возвращает 0 и печатает JSON валидации. Установка загружает зависимости, если нет подготовленного кэша wheels. Сама валидация не загружает удалённые схемы: registry запрещает внешние ссылки. Зафиксированные версии пакетов не означают фиксацию хешей, аудит уязвимостей или воспроизводимую бинарную сборку. Сохраните весь каталог `schemas` рядом со скриптом.

## CLI

```text
python3 validate_report.py REPORT
  [--max-report-bytes N] [--max-errors N]
```
| Аргумент | По умолчанию | Назначение |
|---|---|---|
| `REPORT` | Обязателен | Обычный UTF-8 JSON-файл; symlink отвергается |
| `--max-report-bytes` | `16000000` | Предел чтения отчёта, отдельно от бюджета содержимого сканера |
| `--max-errors` | `32` | Максимум сохраняемых диагностических записей |

Лимиты должны быть положительными целыми. Глубина JSON ограничена 64 уровнями. Повторные ключи на любой глубине, неверные UTF-8/JSON, BOM, NaN/Infinity, чрезмерная вложенность и специальные файлы приводят к отказу. Для обнаружения превышения размера читается один дополнительный байт сверх заданного максимума. Не повышайте пределы без оценки ресурсов процесса.

## Коды выхода и результат

```json
{
  "valid": true,
  "kind": "report",
  "scanner_exit_code": 0,
  "errors": [],
  "errors_truncated": false
}
```
| Код | Значение | Действие потребителя |
|---|---|---|
| `0` | Корректный отчёт, заявленное покрытие полное, находок нет | Продолжить локальное ревью области и происхождения |
| `1` | Корректный отчёт с находками; пробелы могут присутствовать | Разобрать находки и покрытие |
| `2` | Корректный неполный отчёт без находок либо распознанная ошибка запуска | Устранить отсутствие проверки или ошибку входа/политики |
| `3` | Неверный/нечитаемый отчёт либо валидация недоступна | Остановить интеграцию; не подставлять чистый результат |

`valid` означает соответствие контракту, а не одобрение публикации. `kind` принимает `report`, `startup_error` или `invalid`. При неверном входе `scanner_exit_code` равен null. В `errors` есть стабильный `code` и безопасный `location`; `errors_truncated` отмечает ошибки сверх лимита. Координаты обозначают поля контракта и индексы массива, а не исходные пути. Диагностика не содержит значений входа, неизвестных имён полей и текстов исключений. Ошибки синтаксиса аргументов обрабатывает argparse: stderr, код 2, без JSON валидации; закрытый stdout не нормализуется.

Выполните готовые примеры:

```bash
python3 validate_report.py examples/reports/valid/findings.json
python3 validate_report.py examples/reports/valid/empty.json
python3 validate_report.py examples/reports/valid/startup-error.json
python3 validate_report.py examples/reports/invalid/false-clean.json
```
Ожидаемые коды по порядку: 1, 2, 2, 3. Распознанная ошибка запуска корректна по форме, но означает неуспех; она не должна продвигать этап публикации. В POSIX проверяйте `echo $?`, в PowerShell `$LASTEXITCODE` сразу после каждой команды.

## Проверка структуры

[response-0.2.schema.json](../../schemas/response-0.2.schema.json) объявляет Draft 2020-12. Ответ — полный объект отчёта либо точный объект ошибки запуска. Все объекты запрещают дополнительные поля. Проверяются обязательные поля, типы, константы версии/области и числовые границы. Находка должна сохранять статическую серьёзность и рекомендацию своего ID; evidence содержит положительный номер строки и `redacted: true`, без открытого совпадения. Причина пробела определяет обязательность или запрет `asset_id`.

Схема использует только локальные fragment-ссылки. Её можно проверить другой реализацией Draft 2020-12, но внешняя проверка структуры не обеспечивает межполевые условия ниже. Основание: [JSON Schema validation vocabulary](https://json-schema.org/draft/2020-12/json-schema-validation); документация движка: [jsonschema validation API](https://python-jsonschema.readthedocs.io/en/stable/validate/).

## Межполевые условия

| Код | Условие | Зачем |
|---|---|---|
| `coverage_mismatch` | Полное покрытие тогда и только тогда, когда пробелы и исключения пусты | Частичный отчёт не должен заявлять полноту |
| `empty_scope_mismatch` | Ровно один `empty_scope` тогда и только тогда, когда проверено ноль файлов | Пустой обзор не является чистым свидетельством |
| `stop_state_mismatch` | Остановка соответствует пробелу общего лимита; такой пробел максимум один | Сохранить смысл досрочной остановки |
| `file_counter_mismatch` | Проверено ≤ встречено | Отвергнуть невозможные счётчики |
| `file_budget_exceeded` | Встречено ≤ `max_files` | Соблюсти заявленный бюджет |
| `byte_budget_exceeded` | Прочитано байт ≤ `max_total_bytes` | Сохранить учёт общего чтения |
| `finding_budget_exceeded` | Сохранено находок ≤ `max_findings` | Отвергнуть противоречивое сохранение |
| `finding_limit_mismatch` | Пробел лимита находок требует заполненного предела | Превышение должно следовать после сохранённого максимума |
| `finding_without_input` | Находки требуют проверенных файлов и прочитанных байт | Не принимать находку без входа |
| `file_limit_mismatch` | Пробел лимита файлов требует равенства счётчика пределу | Сохранить поведение остановки сканера |

Целые числа следуют числовой семантике JSON Schema: `1.0` — целое значение; `true` — boolean, а не integer. Валидатор не восстанавливает число строк, не доказывает чтение отдельных файлов, не проверяет правильность совпадений и не измеряет precision/recall.

## Безопасная интеграция потребителя

Сначала проверьте код процесса валидатора, затем разберите его JSON. Отсутствующий вывод, неподдерживаемая версия, неверный JSON и код 3 означают сбой интеграции. Храните параметры сканирования и первоначальный код сканера в приватных метаданных конвейера; сравнивайте исходный код с `scanner_exit_code`, если доступны оба. Сам валидатор исходный код процесса не получает и такого сравнения не делает.

Не открывайте пути отчёта на хосте потребителя. Это непрозрачные метки источника: они могут идентифицировать людей и использовать разделитель другой ОС. Храните отчёты приватно. Не публикуйте входы валидации для диагностики; воспроизводите проблему синтетическими фикстурами. Корректный ответ не разрешает публикацию исходного материала.

## Диагностика

| Диагностика | Смысл | Действие |
|---|---|---|
| `input_error` | Нет файла, превышен размер, symlink/специальный файл, неверная кодировка или строгий JSON | Проверить вход локально; подробностей со значениями в выводе нет |
| `dependency_missing` | Не установлена зависимость валидатора | Активировать окружение и установить requirements |
| `validation_unavailable` | Нет поставляемой схемы, она неверна либо движок отказал | Восстановить скрипт и схему из одной проверенной версии |
| `schema_*` | Нарушение структуры | Проверить безопасную координату по контракту; не переименовывать поля вслепую |
| Код согласованности | Счётчики, покрытие и остановка противоречат друг другу | Воспроизвести из вывода сканера; проверить производителя и передачу |
| `errors_truncated: true` | Ошибок больше сохранённого числа | Исправить показанные и повторить либо обосновать повышение лимита |

## Воспроизведение проверок качества

```bash
python3 -m unittest discover -v
python3 check_docs.py
```
Полный набор содержит 37 тестовых методов: 22 для сканера и 15 для валидатора. Пятнадцать размеченных отчётов охватывают восемь корректных и семь некорректных ответов в [manifest.json](../../examples/reports/manifest.json). Это сценарии контракта, а не измерение точности обнаружения раскрытия. `check_docs.py` проверяет имена страниц RU/EN, локальные ссылки, совпадение команд, последовательность 1 → 0 руководства сканера, соответствие примера отчёта схеме и примеры валидатора.
